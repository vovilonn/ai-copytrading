# AI копитрейдинг-платформа — дизайн

Дата: 2026-07-10 · Статус: на согласовании

Документ описывает, что и почему мы строим. Реализация разбита на фазы в §16.
Развёрнутые исследования, на которых он стоит, лежат в `docs/superpowers/research/`.

---

## 1. Задача и границы

Платформа читает торговые сигналы из Telegram-каналов, понимает их (детерминированный
парсер + AI с чтением картинок) и исполняет на Bybit, а оператор видит всё в веб-админке.

**Источники на старте:**

- канал `2088626562` — регулярные шаблонные сигналы;
- форум `1962583820`, топик «A TRADING» (`173666`) — свободный чат.

Добавление третьего канала — новый адаптер, ядро не трогается.

**Вне границ:** собственная стратегия, мультибиржевость, мобильное приложение.

**Честный контекст риска.** Копирование чужих сигнальных каналов почти всегда имеет
отрицательное матожидание для подписчика: автор входит раньше, чем публикует; задержка
парсинга съедает край. Технически задача чистая, но под реальные деньги система, скорее
всего, аккуратно исполнит убыточную стратегию. Поэтому dry-run — не факультатив, а
обязательный первый режим, и переход на mainnet принимается по данным из §16 Ф4.

## 2. Что проверено вживую

Всё ниже подтверждено запросами к реальным API и разбором 200 выгруженных сообщений,
а не документацией по памяти.

**ai-proxy** (`http://127.0.0.1:8317`, Claude-подписка):

- `tool_choice: {type: "tool"}` даёт валидный structured output — 460 вызовов, 0 отказов;
- vision работает; символ терсных сообщений читается с картинки;
- **поле `system` молча игнорируется.** Инструкции и схему кладём первым `text`-блоком
  user-turn с `cache_control: {type: "ephemeral"}`;
- prompt caching работает на user-блоках (`cache_creation` → `cache_read`);
- прокси добавляет ~1370 входных токенов Claude Code в каждый запрос;
- прокси — единственная точка отказа, наблюдался HTTP 502.

**Bybit** (testnet, ключи в `.env`):

- аккаунт UTA 2.0, one-way (`positionIdx=0`), `marginMode=REGULAR_MARGIN`, баланс пуст;
- ключ **мастер-ключ** (`isMaster: true`) с правами `AccountTransfer` + `SubMemberTransfer`;
  субаккаунтов пока 0, переводы доступны;
- в UTA режим маржи **аккаунт-уровневый**, не по-символьный;
- приватный и публичный WS отвечают: `auth` + `subscribe` на `position.linear`,
  `order.linear`, `wallet`, `tickers.<symbol>`;
- повторный `set-leverage` тем же значением → `retCode 110043`; дубль `orderLinkId` → `110072`.
  Оба трактуем как идемпотентный успех. *(источник — доки; live не воспроизвести на пустом счёте)*
- `GRASSUSDT`, `EIGENUSDT` на testnet существуют, но `status=Closed` → гейт `status == 'Trading'`,
  причина пропуска `symbol_not_trading`;
- `maxLeverage` расходится между сетями (`LITUSDT` TN 50 / MN 25; `APTUSDT` TN 25 / MN 50) —
  клампим по инструменту той сети, где исполняем.

**Telegram** (read-only подключение под рабочей сессией, GramJS 2.26):

- надёжный признак ответа в топике — **`replyToTopId`**, а не `replyToMsgId`:
  настоящий ответ ⟺ `replyToTopId != null`; обычный пост в топик ⟺
  `replyToTopId == null && replyToMsgId == 173666`. Проверено на `221445`, `221452`, `221365`;
- `NewMessage({chats})` фильтрует только по `chatId`; топик отсеивается вручную;
- бэкфилл `getMessages(entity, {minId, reverse, replyTo: topicId})` возвращает ровно пропущенные
  сообщения топика;
- **`catchUp()` в GramJS — пустая заглушка**, `getDifference` отсутствует. Библиотека не
  восстанавливает пропуск после обрыва и может продиспатчить сообщение дважды. Gap-recovery —
  только наш бэкфилл, дедуп по `(channel_id, message_id)` обязателен;
- «Error: TIMEOUT» из `updates.js` — это keepalive-пинг, а не сбой: за ним следует
  авто-реконнект. Гасится `setLogLevel(WARN)`;
- альбом приходит **N отдельными апдейтами**; подписи может не быть вовсе (`221378–221381`);
- фото ~98 КБ / 1128 px — ресайз не нужен. Видео в vision не отправить, берём thumbnail;
  `downloadMedia(msg, {thumb: -1})` качает **весь mp4**, нужен `thumbs.find(t => t.className === 'PhotoSize')`;
- **24 из 25 сообщений топика имеют `editDate`** — правки это норма, а не край;
- порядок обработки — по `message.id`, не по `date`: у элементов альбома `date` одинаков.

## 4. Изоляция каналов: субаккаунт на канал

Bybit в one-way держит одну нетто-позицию на символ. Каналы реально пересекаются: 30 июня
оба держали SOL long одновременно (форум с 12:39, канал с 14:34, закрыт в плюс). На одном
аккаунте один из сигналов был бы потерян, а «стоп в б/у» от одного канала сломал бы сделку
другого.

**Решение: каждому каналу — свой субаккаунт Bybit** со своими ключами, equity, плечом и
режимом маржи. Это даёт:

- полную изоляцию позиций и ликвидации: просадка одного канала не двигает liq другого;
- реализуемость тумблера «Allow cross margin» из дизайна — режим маржи аккаунт-уровневый,
  а аккаунт теперь свой у каждого канала;
- осмысленную базу риск-процента: «Риск: 1.5%» считается от equity субаккаунта канала;
- рабочий фильтр Margin на странице Positions.

Цена: провижининг. Скрипт `pnpm bybit:setup` создаёт субаккаунт и ключи под каждый канал
(`POST /v5/user/create-sub-member`, `/v5/user/create-sub-api`) и переводит туда средства
(`/v5/asset/transfer/universal-transfer`). Ключи субаккаунтов хранятся в БД, зашифрованные
`ENCRYPTION_KEY` из `.env`.

Внутри канала действует прежнее правило: один символ — одна открытая сделка.

## 5. Топология процессов

Объём низкий (2–3 сигнала в день на канал), а требования строгие: строгий порядок на канал,
единственный писатель на биржу, единственная MTProto-сессия. Поэтому единая кодовая база
(pnpm workspace) и три однoинстансных процесса.

```
tg-ingest  ──INSERT messages + NOTIFY──►  engine  ──Bybit REST/WS──►  Bybit
(GramJS,                                 (пайплайн, state,
 1 сессия)  ◄──last_seen watermark────    execution, recon,
                                          scheduler)
                                              │ domain_events
                                              ▼
browser ◄── socket.io / REST ──  api  ── LISTEN domain_events
```

- **`tg-ingest`** держит единственную MTProto-сессию. Ровно одна реплика: две сессии с одним
  auth-key дают потерю апдейтов и риск `AUTH_KEY_DUPLICATED`. Падение Telegram не роняет
  исполнение. Бэкфилл запускается на старте и после **каждого** реконнекта, потому что
  `catchUp()` в GramJS ничего не делает. Альбом собирается буфером по `groupedId` (окно 600 мс)
  и уходит дальше одним сообщением.
- **`engine`** — единственный, кто пишет на биржу. Это резко упрощает rate-limit,
  идемпотентность и порядок.
- **`api`** — REST + WS-мост, не пишет ни на биржу, ни в state; только читает БД и
  ретранслирует `domain_events`.

Шина — сам Postgres: durable-очередь на `FOR UPDATE SKIP LOCKED`, `LISTEN/NOTIFY` для
латентности, транзакционный outbox. Redis не вводим: единственный stateful-сервис —
Postgres, и лишний SPOF не нужен.

Все деньги, цены и количества — `NUMERIC`, никогда float. Доступ к БД — Kysely + `pg`
(нужны `SKIP LOCKED` и advisory-lock, с которыми Prisma неудобна).

## 6. Пайплайн обработки сообщения

```
Telegram → нормализация → адаптер канала (regex) ─┐
                                                  ├→ reconciler → risk → execution → Bybit
                        AI (Sonnet, текст+фото) ──┘        │
                                                            └→ state (trades, legs, ownership)
```

Ключевой принцип: **AI извлекает намерение, детерминированный код принимает денежные
решения.** LLM не считает арифметику. Всё, что нужно вычислить (безубыток = средняя цена
входа, «один объём», «с текущих»), она отдаёт символьным маркером, а число подставляет код
из состояния позиции.

**Reconciler** сливает вывод парсера и AI в единое решение:

- парсер главный по числам, которые он извлёк из текста;
- AI главная по символу (особенно с картинки), типу действия и мульти-action разбиению;
- расхождение по числу действий или по символу → `needs_review`, ордера не уходят;
- канонический `actionIndex` назначает reconciler, а не каждый парсер отдельно — иначе
  разные нумерации дадут разные `orderLinkId` и идемпотентность развалится.

Поле `Method` в UI: `Auto parsing`, если решение целиком пришло от парсера; `AI parsing`,
если что-то добавила модель.

## 7. AI-слой

Замерено на всех 200 реальных сообщениях (460 вызовов, 0 отказов).

| Модель | F1 по извлечению (30 сложнейших сообщений) | Цена / 1000 сообщений |
|---|---|---|
| Haiku 4.5 | 0.816 | — |
| Sonnet 4.5 | 0.891 | $11.65 |
| Opus 4.8 | 0.922 | — |

**Двухступенчатая схема haiku→sonnet отвергнута эмпирикой.** Классификатору нужны картинки
(иначе не понять `2🎯`), а с картинкой haiku теряет 2–4.5% реальных действий — в том числе
«стоп в б/у», спрятанный в конце `#BTC обзор`. При этом two-stage выходит дороже
($12.03 против $11.65). Требование «не упустить ни один action» дисквалифицирует haiku как
отсекающий гейт.

**Схема:** одна ступень — **Sonnet 4.5** на все сообщения, кроме жёсткого текстового шума
(zoom-ссылки, реф-ссылки). Эскалация на **Opus 4.8** при `needs_human`, `symbol == UNKNOWN`
или `confidence < 0.7`.

Промпт: инструкция + JSON-схема инструмента первым `text`-блоком user-turn с
`cache_control`. В контекст подаются текст, `t_msg`, **список открытых позиций этого канала**
(без него дельты не резолвятся) и картинки в base64. Альбом собирается по `groupedId` с
таймаутом и уходит одним вызовом.

Отказ прокси не теряет сообщения: канал 2088626562 продолжает работать на детерминированном
парсере, форум уходит в `needs_review` с алертом. Разбор кэшируется по нормализованному
тексту и хэшам картинок.

## 8. Сайзинг и плечо

Чистые функции, без I/O. Проверяются свойствами: `liq` всегда за `SL`, `notional` не
превышает потолок, `qty` кратно `qtyStep`.

```
stopDistance = |entry − SL| / entry

есть Риск% и SL  →  notional = (Риск% × equity_субаккаунта) / stopDistance
нет Риск%        →  notional = Trade size канала                  (фолбэк)
нет SL           →  входим со страховочным SL (см. ниже)

notional = min(notional, equity_субаккаунта × Max leverage)       (жёсткий потолок)
qty      = округлить_вниз(notional / entry, qtyStep)
```

«Риск: N%» встречается только в канале 2088626562; форум всегда идёт по фолбэку.
`entry` для лимитки — цена лимитки, для market — текущая цена.

**Плечо.** Ликвидация для isolated:

```
long:   liq ≈ entry × (1 − 1/L + mmr)
short:  liq ≈ entry × (1 + 1/L − mmr)
```

Отсюда максимальное плечо, при котором стоп срабатывает раньше ликвидации:

```
L_max_by_SL = 1 / (stopDistance + mmr)
L = min( default_leverage, L_max_by_SL × SAFETY, channel.max_leverage, instrument.maxLeverage )
L = округлить_вниз(L, leverageStep);   L < 1 → Skipped
```

`SAFETY` = 0.8. `mmr` берётся из тира risk-limit инструмента. В cross-режиме ликвидация
зависит от equity всего субаккаунта, поэтому формула по isolated консервативна — она
ошибается в безопасную сторону. Реальный `liqPrice` дополнительно мониторится из потока
позиций, сближение с SL даёт алерт.

**Вход без SL** (типично для форума: стоп приходит отдельным поздним сообщением). Входим
сразу, ставим собственный страховочный SL, рассчитанный от дефолтного плеча; когда автор
пришлёт свой стоп — заменяем. Позиция ни секунды не висит без защиты, ни один сигнал не
теряется.

**Доборы.** Каждый добор — отдельная лега со своим `qty`, сайзится тем же правилом.
Совокупный notional по символу ограничен тем же потолком. «Один объём» = `qty` одной леги,
«фикс половину» = 50% текущего размера позиции.

## 9. Исполнение

**Вход диапазоном.** Цена внутри диапазона → market. Цена ещё не дошла → limit на ближнюю
границу. Цена ушла за диапазон → `Skipped: price_out_of_range`. Диапазон нормализуется в
`[min, max]`: в дампе он записан то по возрастанию, то по убыванию, и порядок не коррелирует
со стороной.

**Тейки.** Цели берутся из сообщения; если целей нет — ставим свои дефолтные. Ставятся на
бирже как `reduceOnly` limit-ордера — у каждого свой `orderLinkId` и полная наблюдаемость
через `order/realtime`, в отличие от `tpslMode=Partial`. Стоп — отдельным `trading-stop`
`Full`, чтобы гарантированно закрыть остаток. Всё живёт на бирже и сработает, даже если бот
лежит.

Если позже приходит сообщение, меняющее ещё не сработавшие TP или SL — двигаем ранее
выставленные ордера (`amend`), а не создаём новые.

Сообщения вида «зафиксировал 50%» трактуются как **события** (наша лесенка уже отработала),
а не как команды. Командами являются только явные указания: «закрываю остаток», «стоп в б/у»,
«sl 74». Иначе получаем двойное закрытие. Расхождение нашего размера с авторским пишется в
лог как дрейф.

**Отложенные лимитки.** Отменяются явным сообщением («лимитка не актуальна», «другие лимитки
больше не актуальны»). TTL = 7 дней — защитный потолок, а не основной механизм: в дампе автор
держал лимитку на BTC 61000 трое суток.

**Идемпотентность.** `orderLinkId` выводится из координат сообщения, а не из свежесозданного
`tradeId`:

```
orderLinkId = <prefix><channelOrd>-<tgMessageId>-<actionIdx>-<purpose><legIdx>
пример:      K02-221452-00-E0            (≤36 символов, [A-Za-z0-9_-])
```

`legIdx` — чистая функция от сообщения: для TP это индекс цели в `tps[]`, для входа и добора
всегда `0` (пары `tgMessageId + actionIdx` достаточно). Никогда не выводится из текущего числа
лег — иначе рестарт сдвинет индекс и создаст второй ордер.

`prefix` = `K` для live и `D` для dry-run: при переключении режима реконсиляция не примет
симулированные ордера за реальные. `TR-1042` — только человекочитаемый ярлык, в ключе не
участвует.

Переход `message.status: pending → executing → executed` фиксируется в одной транзакции до
вызова биржи. `110072` (дубль `orderLinkId`) и `110043` (плечо не изменилось) считаются
успехом.

**Внешние изменения.** По событию `position.size → 0` из приватного WS — `cancel-all` по
символу, освобождение владения символом, закрытие сделки. Это покрывает и ручное закрытие
человеком в терминале Bybit, и срабатывание стопа.

## 10. Модель данных

Полный DDL — в `docs/superpowers/research/backend-architecture.md` §2. Ядро:

| Таблица | Назначение |
|---|---|
| `channels`, `channel_settings` | источники и их настройки из UI; ключи субаккаунта |
| `messages`, `message_media` | сырьё; `reply_to_top_id`, `is_topic_message`, `edit_date`, `ai_summary` |
| `parse_results`, `ai_calls` | вывод парсера и модели, токены, стоимость, латентность |
| `actions` | распознанные действия, по одному на строку таблицы Actions |
| `trades`, `trade_legs` | сделка `TR-1042` и её леги (вход + доборы) |

| `positions` | зеркало биржи |
| `symbol_ownership` | атомарный захват символа внутри канала, ключ `(channel_id, symbol)` |
| `processed_messages` | дедуп `(channel_id, message_id)` |
| `audit_log`, `domain_events` | наблюдаемость и шина для UI |

Обязательные поля, вскрытые проверкой: `messages.reply_to_top_id` (без него в реалтайме
теряется 14% дельт форума), `messages.ai_summary` (таймлайн рисует саммари на уровне
сообщения), `trades.avg_entry` (безубыток считается от средней по легам, а не от первого входа).

**Конкурентность.** Захват символа — атомарный `INSERT ... ON CONFLICT DO NOTHING` в
`symbol_ownership` по ключу `(channel_id, symbol)`. Обработка строго последовательна в пределах
канала (advisory-lock по `channel_id`), а сообщения применяются по возрастанию `message.id`:
после бэкфилла «закрыл» может прийти раньше «открыл».

## 11. Реалтайм

Backend подписан на приватный WS Bybit (`position`, `order`, `execution`, `wallet`) и
публичный (`tickers.<symbol>`). Браузер к Bybit не ходит — только к нашему `api`.

События сервер → клиент: `positions.snapshot`, `position.upsert`, `position.close`,
`ticker.update`, `message.new`, `message.parsed`, `action.new`, `action.skipped`,
`channel.stats`, `execution.mode`, `order.pending`, `order.resolved`.

`ticker.update` коалесцируется до ~10/с на символ: странице Positions это даёт ощущение
живого стрима, как на Bybit, без перерисовки таблицы сотни раз в секунду. Обрыв WS →
переподключение с backoff и ре-гидратация через `positions.snapshot`.

`TradeRef` хранится и передаётся как `TR-1042`; `#` добавляет фронт при рендере, а поиск
его срезает.

## 12. Фронтенд

React (Vite) + shadcn + Tailwind, тёмная тема, 1:1 с `design/project/Admin.dc.html`.
Источник правды — HTML, не скриншоты (это прямо сказано в `design/README.md`).

Экраны: Login, Channels, Channel → Messages, Channel → Settings, Actions, Positions.
Плюс мобильный bottom nav, хлебные крошки, пустые состояния.

Токены: фон `#000`, карточка `#0d0d0f`, границы `rgba(255,255,255,.07)`, акцент `#ff6a1f`,
long `#34d399`, short `#fb7185`, skipped `#fbbf24`. Шрифт Exo 2 (лежит в
`design/project/uploads/Exo_2/`), моно — системный стек. Иконки только lucide-react.

Состояние — TanStack Query; фильтры живут в URL (в прототипе они в стейте компонента, но
так ссылка на отфильтрованный список становится шарящейся). WS патчит кэш напрямую.

**Типы действий.** Бэкенд знает 12 типов, прототип рисует 4. Маппинг использует иконки,
которые дизайнер объявил в `lucide-icon.js`, но не задействовал — это и есть их назначение:

| Действие | Иконка |
|---|---|
| `open` long / short | `trending-up` / `trending-down` |
| `add` | `circle-plus` |
| `close`, `close_all` | `circle-x` |
| `partial_tp` | `target` |
| `partial_close` | `scissors` |
| `modify_sl` | `shield` |
| `modify_tp` | `target` |
| `cancel_order` | `circle-minus` |
| `tp_hit`, `sl_hit` | события, рисуются строкой саммари, а не действием |
| `hold` | строки нет |

**Пробелы прототипа и минимальные решения:**

- кнопка Settings в сайдбаре без обработчика → экран с режимом исполнения и статусами
  подключений (Telegram, Bybit, ai-proxy);
- Win Rate требует истории закрытых сделок, которой в прототипе нет → считается как
  `closed_wins / closed_trades` по realized PnL; до накопления истории показывает `—`;
- `Skipped` без причины → бейдж получает тултип с `reason` (`symbol_not_trading`,
  `price_out_of_range`, `symbol_busy`, `needs_review`);
- отложенные лимитки не видны нигде → строка `order.pending` на Positions с таймером TTL;
- нет индикатора dry-run → бейдж в топбаре по событию `execution.mode`.

## 13. Отказоустойчивость

| Сценарий | Механизм |
|---|---|
| Рестарт с открытыми позициями | Старт-реконсиляция: `position/list` + `order/realtime` сверяются с журналом; расхождение → `needs_review`, а не автокоррекция |
| Обрыв Telegram на час | Бэкфилл от `channels.last_seen_message_id` через `getMessages({minId, reverse, replyTo})`, дедуп по `(channel_id, message_id)`, обработка строго по возрастанию `message.id` |
| Падение ai-proxy | Канал 2088626562 работает на парсере; форум → `needs_review` + алерт. Сообщения не теряются |
| Отклонение ордера биржей | Ордер → `rejected`, сделка → `needs_review`, алерт. Повторов нет |
| Ручное закрытие в терминале Bybit | `position.size → 0` из WS → `cancel-all` по символу, освобождение владения |
| Удаление сообщения | Неисполненную лимитку снимаем; открытую позицию **не закрываем** — удаление поста не отменяет рыночный риск. Алерт оператору |
| Условный ре-вход («на случай стопа лимитка ниже стопа») | Не исполняем: лимитка залилась бы сразу после стопа и дала двойную экспозицию. → `needs_review` |
| Символ не определён при 2+ открытых позициях и недоступном vision | `needs_review`. Эвристика «последний тронутый символ» доказанно промахивается на `221447` |

**Правки сообщений.** 24 из 25 сообщений топика имеют `editDate` — автор постоянно дописывает
посты. Поэтому «любая правка → `needs_review`» парализовала бы систему. Вместо этого правка
переразбирается и **диффится против исполненной версии**:

- изменились цены ещё не набранной сделки (лимитка висит) → переставляем ордера;
- добавлена отмена или «не актуально» → трактуем как команду закрытия;
- изменились числа уже исполненного действия → `needs_review`;
- всё остальное (дописан комментарий, «TP1 hit ✅») → только лог.

Хранится `(message_id, edit_date, parsed_version)`; повторный `edit_date` игнорируется.

## 14. Безопасность и конфигурация

Один админ: логин и bcrypt-хеш пароля в `.env`, JWT в httpOnly cookie, тот же guard на WS.

В `.env`: доступы (Telegram, мастер-ключ Bybit, `ENCRYPTION_KEY`), `EXECUTION_MODE`,
пороги гвардов. В БД: всё, что редактируется в UI (настройки канала), и ключи субаккаунтов
в зашифрованном виде. Конфиг валидируется zod-ом на старте — падаем сразу, не в рантайме.

`EXECUTION_MODE` — единственная точка ветвления: порт `ExecutionPort` с двумя реализациями,
`DryRunAdapter` и `BybitAdapter`. Dry-run пишет те же строки в БД и рисует те же экраны, но
не звонит на биржу. Никаких `if (dryRun)` по коду.

## 15. Тестирование

- **Юнит** — сайзинг и плечо как чистые функции, проверка свойствами: ликвидация всегда за
  стопом, notional не превышает потолок, qty кратно шагу.
- **Интеграция** — 200 выгруженных сообщений как фикстуры. Парсеры прогоняются на них в CI;
  отдельно проверяется, что ни один `#BTC обзор` не распознан как сигнал.
- **Ингест** — сборка альбома без подписи, различение `root`/`reply` по `replyToTopId`,
  повторная доставка одного `message_id` не создаёт вторую сделку, бэкфилл после реконнекта
  не дублирует уже обработанное.
- **AI** — записанные ответы (VCR) для детерминизма; golden set из 30 сложнейших сообщений
  форума с метрикой F1 в CI, чтобы ловить регрессии промпта.
- **E2E** — Bybit testnet: открытие, лесенка TP, перенос стопа, частичное закрытие, ручное
  закрытие в терминале → `cancel-all`, `kill -9` между outbox и отправкой → реконсиляция без
  дублей.

Testnet требует пополнения через faucet и не даёт торговать `GRASSUSDT`/`EIGENUSDT`
(`status=Closed`), поэтому e2e идёт на `BTCUSDT`/`SOLUSDT`/`ETHUSDT`.

## 16. Фазы

Каждая фаза — вертикальный срез Telegram → разбор → состояние → исполнение → UI. Её можно
показать и она снимает названный риск. Следующая добавляет глубину, не переписывая предыдущую.

**Ф0 — Скелет и живая лента.** Конфиг, миграции всей схемы, наблюдаемость, auth, api, web
(экраны Channels и Messages), `tg-ingest` с реалтаймом, бэкфиллом, альбомами и фильтром топика.
*Демо:* оператор логинится и видит живую ленту обоих каналов.
*Снимает:* весь Telegram-слой, инфраструктуру, каркас реалтайма.

**Ф1 — Детерминированный разбор канала 2088626562 в dry-run.** Нормализация, адаптер CH1,
reconciler, sizing/leverage, `DryRunAdapter`, state (сделки, леги, владение символом), экраны
Actions и Positions.
*Демо:* прогон дампа → в UI появляются действия с `TR-x` и симулированные позиции; повторный
прогон не создаёт дублей.
*Снимает:* идемпотентность, корректность денежной математики.

**Ф2 — AI-слой и форум.** Клиент ai-proxy, промпт с кэшированием, эскалация, vision, адаптер
CH2, `needs_review`.
*Демо:* `2🎯` и `Фикс половину` превращаются в действия с правильным символом.
*Снимает:* семантику «объёмов», атрибуцию символа, деградацию при падении прокси
(проверяется его выключением).

**Ф3 — Live-исполнение на testnet.** Провижининг субаккаунтов, `BybitAdapter`, мост WS,
реконсиляция, планировщик, `cancel-all`.
*Демо:* реальные ордера на testnet, полный жизненный цикл сделки.
*Снимает:* интеграцию с биржей, рестарт с позициями, ручные вмешательства.

**Ф4 — История, наблюдаемость, полировка.** Realized PnL и Win Rate, экран отложенных
лимиток с TTL, экран Settings, метрики, реплей-бэктест на дампе.
*Демо:* отчёт «сколько входов отсеяли бы гварды и каков был бы PnL».
*Снимает:* решение о переходе на mainnet принимается по данным.

## 17. Осознанно принятые риски

- `110072` и `110043` как признаки успеха взяты из документации: на пустом testnet-счёте
  живьём не воспроизвести. Проверяется в Ф3.
- Формула ликвидации применяется по isolated даже в cross. Это консервативно, но реальный
  `liqPrice` всё равно мониторится из потока позиций.
- Задержка Sonnet p95 ≈ 13 с. Для входов «с текущих» это сдвигает цену; гвард на протухший
  сигнал (`STALE_AFTER_SEC`) и на неблагоприятный дрейф (`MAX_ADVERSE_DRIFT`) пропустит вход,
  вместо того чтобы гнаться за ценой.
- Наша лесенка TP и ручные доли автора могут разойтись по размеру. Мы следуем своей лесенке,
  дрейф пишем в лог. Альтернатива — зеркалить автора — ломается при падении бота.
- `#BTC обзор` иногда прячет дельту в последней строке. Поэтому обзоры не отсекаются заранее,
  а уходят в AI целиком.
