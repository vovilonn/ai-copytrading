# Субаккаунты Bybit на канал — дизайн

## Задача

Сегодня движок торгует **одним** аккаунтом на все каналы: `main.ts` поднимает единственный
`BybitRestClient` и единственный приватный WS из `BYBIT_API_KEY`. Колонки
`channels.bybit_api_key_enc/bybit_api_secret_enc/bybit_sub_uid` существуют с первой миграции, но
их никто не пишет, а `getChannelKeys(db, channelId)` не вызывается ниоткуда.

Из-за этого включение двух каналов сразу опасно на пересекающихся символах: позиции неттингуются
на одном аккаунте, пуши достаются произвольному каналу (`attributeSymbol` берёт первого владельца
символа), а риск-сайзинг каждого канала считается от общего депозита.

Цель — дать каждому каналу собственный аккаунт Bybit, сохранив текущее поведение для каналов без
своих ключей.

## Модель

**Аккаунт — это набор кредов, а не канал.** Канал ссылается на аккаунт своими зашифрованными
ключами; каналы без ключей обслуживает «общий» аккаунт из `BYBIT_API_KEY` — ровно сегодняшнее
поведение, то есть миграция никого не ломает.

**Каналы с одинаковым `apiKey` обслуживает ОДИН рантайм** (один REST-клиент, один приватный WS,
один кэш equity). Это не оптимизация, а корректность: два WS-соединения на один аккаунт получали
бы одни и те же пуши и обрабатывали бы каждый филл дважды. Побочно это же даёт заказчику режим
проверки — прописать двум тестовым каналам одни и те же demo-креды и убедиться, что маршрутизация
работает, не заводя реальных субаккаунтов.

## Компоненты

### 1. `engine/src/runtime/account-registry.ts` (новый)

```
AccountRuntime {
  fingerprint: string        // sha256(apiKey) — идентификатор аккаунта в логах и курсорах
  channelIds: number[]       // какие каналы обслуживает
  rest: BybitRestClient
  executionPort: ExecutionPort
  privateWs: BybitPrivateWs
  equity: string             // обновляется своим таймером
}

AccountRegistry {
  build(db, network, mode) -> Registry   // читает каналы, группирует по fingerprint
  forChannel(channelId) -> AccountRuntime | null
  all() -> AccountRuntime[]
}
```

Реестр строится один раз при старте. Канал, чьи ключи не расшифровались или отвергнуты биржей, в
реестр не попадает: его сообщения не обрабатываются (лог + пропуск), остальные каналы работают.
Падать целиком нельзя — один неверный ключ не должен останавливать торговлю всех.

### 2. Ключи канала

- Запись — CLI `pnpm channel:keys --channel <id> --key <k> --secret <s>`: проверяет ключ живым
  `GET /v5/account/wallet-balance`, шифрует `encryptSecret()` (AES-256-GCM под `ENCRYPTION_KEY`,
  уже реализовано) и пишет в `channels.*_enc`. Отдельная команда `--clear` возвращает канал на
  общий аккаунт.
- Чтение — существующий `getChannelKeys(db, channelId)` с фолбэком на env.
- **Вне объёма:** экран ключей в админке (CLI безопаснее: секрет не идёт через браузер и логи
  запросов) и автоматический провижининг субаккаунтов мастер-ключом Bybit (на demo субаккаунтов
  нет, на mainnet это разовая ручная операция — CLI принимает уже готовые ключи).

### 3. Места, где сегодня зашит один аккаунт

| Место | Сейчас | Станет |
|---|---|---|
| `main.tick()` | один `deps` на все каналы | `deps` строится под канал: порт и equity его аккаунта |
| Таймеры equity / wallet-snapshot | один клиент | по одному на рантайм; снапшот подписывается `channel_id`, если рантайм обслуживает ровно один канал |
| `sweepExpiredLimitOrders` | один порт на все ордера | ордера группируются по каналу, отменяются портом его аккаунта |
| `reconcileOnStart(db, rest)` | сверяет ВСЕ live-сделки против одного аккаунта | `reconcileOnStart(db, rest, { channelIds })` — сверка ограничена каналами аккаунта |
| `private-ws` `attributeSymbol` | ищет владельца символа глобально | ограничен `channelIds` своего соединения |
| Курсоры догона истории (`app_state`) | один ключ на весь движок | ключ включает fingerprint аккаунта |

Скоуп реконсиляции — самое опасное место: без него сверка аккаунта A увидела бы «сделки канала B
без позиции на бирже» и закрыла бы их. Поэтому `channelIds` обязателен во всех шагах (А, Б, Б2, В, Г).

Курсоры без fingerprint означали бы, что два аккаунта делят один водяной знак и половина истории
теряется. Общий (env) аккаунт сохраняет прежний ключ курсора — его история не обнуляется.

## Потоки данных

Вход сообщения не меняется: `tick()` → `withChannelLock(channelId)` → `processChannel(db, channelId,
depsFor(channelId))`. Ордер уходит через порт **аккаунта этого канала**, филл прилетает на WS
**того же аккаунта**, атрибуция ограничена его каналами, зеркало позиции по-прежнему ключуется
`(channel_id, symbol)`.

## Обработка ошибок

- ключ канала не расшифровался / отвергнут биржей → канал не обслуживается, остальные работают;
- рантайм не поднялся (сеть) → тот же путь: лог, канал пропускается, следующий старт повторит;
- дедупликация по `apiKey` защищает от двойной обработки пушей при одинаковых кредах.

## Тестирование

**Unit:** группировка и дедупликация реестра; `forChannel` для канала без ключей → общий рантайм;
скоуп реконсиляции (сделка чужого канала не закрывается); скоуп атрибуции (пуш не уходит в чужой
канал); TTL-свип отменяет ордер портом своего канала; шифрование/дешифрование ключей CLI.

**E2E (живые ордера на demo):** обоим тестовым каналам прописываются ОДНИ И ТЕ ЖЕ demo-креды —
имитация двух субаккаунтов. Прогон всего каталога (16 сценариев) плюс новый сценарий
`ops-two-channels`: оба канала одновременно торгуют РАЗНЫМИ символами, проверяется, что ордера,
сделки и зеркала не перепутались между каналами, а WS-соединение при одинаковых кредах одно.

## Что сознательно не делается

- Админка для ключей и автопровижининг субаккаунтов (см. выше).
- Разные сети у разных каналов: `BYBIT_NETWORK` остаётся общим для движка.
- Изоляция ограничений биржи (rate-limit токен-бакет остаётся на клиента, то есть на аккаунт —
  это и есть правильная гранулярность).
