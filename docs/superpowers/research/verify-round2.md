## 1. Блокер B4 (идемпотентность не от свежего tradeId) — ЗАКРЫТ ПО СУТИ, но с дырой в `legIdx`

**Ключ (backend §4):** `orderLinkId = 'K' + ord2 + '-' + b(tgMessageId) + '-' + actIdx2 + '-' + purpose + legIdx`, пример `K02-221452-00-E0`. Проверил: длина 16–17, charset `[A-Za-z0-9_-]`, ≤36 — верно. `TR-1042` в ключ не входит — правильно, это и закрывает исходный сценарий «краш между отправкой и персистом tradeId».

**Дыра, которую отчёт не закрыл:** поле `legIdx` описано двусмысленно — «уровень лесенки / **номер добора**». Это две разные природы:
- Для TP-лесенки `legIdx` = индекс в массиве `tps[]` распарсенного сигнала → **чистая координата сообщения**, детерминирован. OK.
- Для добора «номер добора» = порядковый номер леги в сделке. Если он берётся из **живого состояния** (`trade_legs.leg_index`, «сколько лег уже есть»), то он НЕ является координатой сообщения. На реальном примере 221428 `"Limit long btc 60850 + limit long btc 60000"` — два добора в одном сообщении; уникальность уже даёт `actIdx` (00, 01), а `tgMessageId` разводит между сообщениями. Если поверх этого `legIdx` считать из числа существующих лег на момент исполнения, то при рестарте с неопределённым персистом предыдущего добора `legIdx` может сдвинуться → **другой orderLinkId → второй ордер → B4 воспроизводится именно на доборах**.

**Решение:** зафиксировать `legIdx` как чистую функцию `(message, parsed intent)`: для TP — индекс цели в `tps[]`; для entry/add — всегда `0` (пары `tgMessageId+actIdx` уже достаточно). Никогда не выводить `legIdx` из текущего числа лег.

**Второй, меньший, зазор:** exactly-once между детерминированным и AI-путём держится только если `actionIndex` берётся из **единого реконсилированного decision** (§1 `reconciler-parse`), а не назначается каждым парсером независимо (иначе разная сегментация → разные `actIdx` → разные id → `UNIQUE` не спасёт). В §4 это подразумевается, но правило «канонической нумерации действий при расхождении числа интентов» не выписано. Требует явной фиксации.

## 2. Блокер B6 (семантика «объём») — модель лег ЕСТЬ, но размер юнита НЕ определён

Проверил на реальных 221371/221426/221382/221359/221407:
- `221371 "Скинул один объем"`, `221426 "Один объем закрыт / Далее 61300, 62200"` — закрытие одной леги. Модель `trade_legs` это выражает.
- `221382 "…Sol 3.2%/2 =1.6 Btc 3.2%/2 =1.6"` — ретроспективный PnL-итог, шум (не действие). OK.
- `221359 "…лучше оставить один обьем в сделке"` — **гипотетика/размышление**, reply на 221346 (проверено живьём: genuine reply). Не команда. Модель лег не помогает — это про роутинг в noise/needs_review, а не про размер.
- `221407 "Твх сместилась потому что четвертинка оставалась после прошлой сделки"` — **это ломает leg-модель**: «четвертинка» (0.25) от ПРОШЛОЙ сделки переносится в текущую и двигает `avg_entry`. В backend это возможно только если старая сделка формально не закрылась (`size` не дошёл до 0) → одна непрерывная `TR-x` с пересчётом `avg_entry` (gap #7, поле `trades.avg_entry` есть — это плюс). Но тогда «объём» и «четвертинка» сосуществуют: **лега (дискретный юнит) vs доля текущего размера** — в одном канале.

**Что не закрыто:** DDL-комментарий «один объём = qty одной леги» не отвечает *какой* леги и *какого размера*. Наши леги сайзятся НАШИМ `trade_size`/риском и по qty НЕ совпадают с ментальными «объёмами» автора (у него цены разные → qty разный). При позиции из 2.5 «объёмов» (из-за четвертинки-переноса) «закрыть один объём» неоднозначно. `backend §channel_settings.mirror_manual_fraction` — про доли, не про юниты. **B6 закрыт лишь наполовину: leg-модель необходима, но правило «размер одного объёма» остаётся вопросом к заказчику** (совпадает с прошлым Q4 — не выношу как новый вопрос, но помечаю как незакрытый блокер).

## 5. WS-контракт backend §6 vs frontend-inventory §7 — расхождения (не «дословно»)

Совпадают 1:1: `positions.snapshot`, `position.upsert`, `ticker.update`, `message.new`, `message.parsed`, `action.new`, `channel.stats`, `action.skipped`, `execution.mode`. Расхождения:

## 6. DDL vs каждый экран дизайна — что выполнимо, где дыра

Пройдено по всем экранам frontend §1/§6/§9. **Выполнимо:** Win Rate (`trades.is_win` FILTER + `status='closed'`, idx `idx_trade_channel_status`), Active Positions (`positions WHERE channel_id=? Это закрыто.

**Дыры/несоответствия DDL↔фронт:**
1. **Нет колонки под AI-summary сообщения.** frontend timeline показывает `sparkles`+`summaryText` на уровне СООБЩЕНИЯ (и для note-строк без действий); `message.parsed.summary?` это несёт. 2. **Settings-форма ↔ `channel_settings`: тип поля.** frontend `ChannelSettings.cross: boolean` (Switch) и REST `PATCH /channels/:id/settings body Partial<ChannelSettings>`. backend по B7 заменил на `equity_share_pct NUMERIC` — **тумблер не мапится на число**. DTO рассинхронизирован: либо форме нужен numeric-input вместо Switch, либо контракт REST разъезжается.
3. **`positions` без `margin_mode`.** Колонка «Leverage + margin chip (Cross/Isolated)» и фильтр Margin (All/Cross/Isolated) в §2. По B7 режим аккаунт-уровневый (один на всё) → chip константен, **фильтр Margin вырожден** (всегда всё или ничего). Либо убрать фильтр, либо явно задокументировать вырожденность.
4. **`/config/runtime` (Settings, gap#1)** возвращает `tgStatus/bybitStatus/aiStatus`, но **источник этих статусов не персистится** (нет поля «TG session connected»); только `channels.status`. Нужен рантайм-хелсчек tg-ingest/engine, сейчас не описан как стор.

## 7. Прогон машины состояний на реальном BTC-сценарии — ГДЕ ЛОМАЕТСЯ

Проверил интерливинг живьём (даты/reply):

- Легиа BTC (limit): 221357(62300)→221364(61800)→**221365(+60000, genuine reply на 221364)**→221412(58100)→221428(60850+60000, +DOGE)→221432(61000, «Другие лимитки больше не актуальны»)→221444(«Long btc с текущих / Лимитка на 61000 остается»)→221448(+61860 + «на 61 лимитка остается на объём»). SOL параллельно: 221443(market long)→221445→221446.

**Точки слома:**

1. **221447 «Фикс половину» (07-09 07:17, фото, reply=173666=топик-пост) — ДОКАЗАННАЯ мис-атрибуция.** На этот момент открыты ДВЕ позиции: BTC (221444) и SOL (221443). Эвристика `lastTouchedSymbol` дала бы **SOL** (последнее касание — 221446 SOL, 07-09 02:06), но **истина = BTC**: следующее 221448 «доливать на точке входа **61860**» — цена BTC, не SOL (~77). То есть без vision `lastTouchedSymbol` промахивается. А vision зависит от `ai-proxy` — SPOF, наблюдался 502. При недоступности AI → `needs_review` → частичное закрытие BTC не исполняется → рассинхрон размера с автором. **Это и есть место, где ломается.**
2. **221445 «Sl 74 / Может быть финальный вынос по битку» — работает ТОЛЬКО если резолвится reply.** Проверил живьём: `replyToMsgId=221443` (SOL-сигнал), `replyToTopId=173666`. Правильно = SOL SL 74 (не BTC; «по битку» — комментарий, не действие; E1 из channel-adapters). Backend берёт reply-parent первым → SOL. НО определить, что это genuine reply (а не топик-пост), можно лишь по `replyToTopId` — которого в DDL нет (п.8).
3. **221446 «Sl Sol 77.16 / На случай стопа ставлю лимитку Sol 76.2» — условный ре-вход НЕ МОДЕЛИРУЕТСЯ.** Лимитка НИЖЕ стопа = ре-вход после срабатывания стопа (gap #6). В `action_type` нет `conditional_reentry`/`stop_and_reverse`, в `orders` нет поля «активировать после стопа». Если поставить лимитку 76.2 сразу и стоп 77.16 сработает → лимитка зальётся → **мгновенный ре-вход / двойная экспозиция**. ОТКРЫТО.

Остальная лесенка (221448 «+61860 лимитка», «на 61 остается на объём») проходит: R2 закрыт `limit_ttl_sec` default 7 дней (лимитка 61000 живёт 07-06…07-09 = 3 дня < 7) + первичная отмена по явным сообщениям. «на объём» снова упирается в неопределённость размера юнита (п.2).

## 8. Заявление о различении «ответ на топик» vs «ответ на сообщение» — ПРОВЕРЕНО ЖИВЬЁМ, отчёт способа НЕ привёл

telegram-отчёт пуст → распечатки raw `replyTo` нет. Подключился read-only и снял сырьё:

```
221445 "Sl 74…"         replyToMsgId=221443  replyToTopId=173666  forumTopic=true   → genuine reply (на SOL-сигнал)
221452 "По битку…"      replyToMsgId=173666  replyToTopId=null    forumTopic=true   → простой пост в топик
221365 "+ limit btc"    replyToMsgId=221364  replyToTopId=173666                     → genuine reply
221443 (SOL-сигнал)     replyToMsgId=173666  replyToTopId=null                       → простой пост
221359                  replyToMsgId=221346  replyToTopId=173666                     → genuine reply
221346                  replyToMsgId=173666  replyToTopId=null                        → простой пост
```

**Надёжный различитель — `replyToTopId`, а НЕ `replyToMsgId`:** genuine reply ⟺ `replyToTopId != null`; простой топик-пост ⟺ `replyToTopId == null && replyToMsgId == topicId(173666)`.

**Две проблемы, которые это вскрывает и которые ни один из отчётов не закрыл:**
1. **DDL хранит только `reply_to_msg_id`, `replyToTopId` не промотирован в колонку** (лежит лишь в `messages.raw` JSONB). Эвристика channel-adapters «`replyToMsgId==173666` ⇒ топик-пост» работает на этих данных **случайно** — потому что все genuine reply целятся в id ≠ 173666. Робастное поле — `replyToTopId`.
2. **Realtime-принадлежность топику ломается без `replyToTopId`.** Проверил: 221445 (genuine reply в топике) имеет `replyToMsgId=221443` — **НЕ 173666**. В realtime `UpdateNewChannelMessage` приходит по всему каналу (все топики). Отфильтровать «это топик 173666?» по `replyToMsgId` нельзя — у reply-внутри-топика он равен id родителя, а не топика. Нужен предикат `replyToTopId==173666 || replyToMsgId==173666`. Ни telegram-, ни backend-отчёт этот realtime-предикат не задают, а DDL не хранит нужное поле → **14% CH2-дельт (genuine reply) в realtime будут пропущены как «не из топика»**.

**Решение:** добавить `messages.reply_to_top_id BIGINT` и `is_topic_message BOOLEAN`; realtime-фильтр и reply-резолвер строить на `replyToTopId`.
