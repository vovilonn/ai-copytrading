# LOOP_STATE

## Goal: сообщение 221563 — пропавший XRP и скипнутая лимитка по ETH

Заказчик: «1 — не открыл xrp позицию, вообще заигнорил ее; 2 — eth лимитку почему-то скипнул,
очевидно же что если стоит лимитка прошлая от автора того же канала и он пишет о новой лимитке то
не надо ее скипать. Адаптируй логи, внеси фиксы чтобы таких кейсов больше не повторялось и добери
прям сейчас по текущим XRP позицию и поставь лимитку».

## Факты прода (msg 221563, канал AACADEMY, 06.08.2026 08:26)

Текст сообщения:

    С текущих long Xrp
    Limit long Eth - 1895
    Limit long SOL - 73.1

Разбор (`parse_results`, parser=deterministic, route=execute): ДВА интента — ETH 1895 и SOL 73.1.
Действия: `open SOLUSDT executed`, `open ETHUSDT skipped(symbol_busy)`. По XRP — НИ ОДНОЙ строки.

## Причина 1: правила B и C стояли в цепочке «первый матч выигрывает»

`parseCh2` = A ?? B ?? C ?? D ?? … . Правило B (лимитки) нашло две строки и вернуло результат —
правило C (рыночный вход, гейт «с текущих») не запускалось вовсе. Строка про XRP исчезла молча:
ни ордера, ни skip, ни следа в UI.

**Фикс** (`ch2.adapter.ts`): B и C объединены в `tryEntries` — по сообщению проходят ОБА сканера,
интенты складываются в порядке строк. Взаимные помехи сняты двумя правилами: строка, отдавшая
лимитку, рыночному сканеру не показывается; символ, уже занятый лимиткой, им пропускается. Если
один из гейтов сработал, но не дал ни одного интента, пока другой дал, — всё сообщение уходит в
AI (`reason=partial_entry_parse`), а не исполняется наполовину.

## Причина 2: «символ занят» — это три разных состояния, а обрабатывались одинаково

`handleOpen` скипал вход, если в `symbol_ownership` висела активная запись канала. Но занятость
бывает разной:

1. позиция реально открыта — дубль сигнала, скип оправдан (защита e2e-сценария `ch1-busy`);
2. висит НЕИСПОЛНЕННАЯ лимитка, автор прислал новую цену — он переставил заявку (ровно случай
   ETH: висела лимитка 1823, пришла 1895);
3. сделка-«призрак»: вход отменён, позиции нет, владение осталось — символ заблокирован НАВСЕГДА
   (на проде так и было: `K02-221553-00-E0` cancelled, а TR-1058 всё ещё держал ETHUSDT).

**Фикс** (`pipeline.ts::resolveBusySymbol`): решение принимается по РЕАЛЬНОЙ экспозиции (позиция +
живые ордера), а не по строке `trades.status`, которая ставится оптимистично в момент отправки
лимитки:

| состояние | новый вход | исход |
|---|---|---|
| позиция открыта | лимитка | `add` — ступень добора (действие переклеивается в тип `add`) |
| позиция открыта | рынок | `skip: symbol_busy` (как раньше — дубль дороже пропуска) |
| висит лимитка, цена ДРУГАЯ | любой | takeover: старые ордера снимаются, сделка → cancelled, вход заново |
| висит лимитка, цена ТА ЖЕ | лимитка | `skip: duplicate_entry` |
| призрак (нет позиции и живых ордеров) | любой | takeover |
| противоположная сторона | любой | `skip: side_conflict` (было `symbol_busy`) |
| `manual_override` | любой | `skip: manual_override` |

## Логи

- каждый `skip` действия пишется в лог с координатами сообщения (`msg N (канал X) SKIP тип символ → причина`);
- решение по занятому символу логируется вместе с причиной и старой/новой ценой;
- `releaseStaleTrade` печатает, что именно снято и что освобождено;
- `warnUncoveredSymbols` — лупа на потерянные инструкции: сообщение что-то исполняет, но в тексте
  упомянута ещё одна торгуемая монета без единого действия → WARN со строкой-источником. Именно
  этот класс дефекта («молча ничего») иначе не находится ни по одной таблице.
