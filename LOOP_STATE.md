# LOOP_STATE

## Goal: «почему тейк не поставил по xrp? сказал нет позы, хотя поза есть»

Финансовая логика. Разбор по systematic-debugging: сначала корневая причина, потом фикс,
потом аудит остальных путей на тот же класс дефекта.

## Что произошло на самом деле

| когда (UTC) | событие |
|---|---|
| 24.10 12:53 | msg 222468 «С хай риском беру Лонги по Xrp и doge, с текущих» — ДВА входа в одном сообщении |
| 24.10 12:53:52 | XRP ушёл на биржу и исполнился: 778.2 @ 1.285, защитный стоп 1.1693 |
| 24.10 12:53:5x | DOGE биржа отвергла: **110007** (не хватило свободной маржи) |
| | исключение вылетело из колбэка `db.transaction()` → **откат всего журнала сообщения** |
| 24.10 23:40 | автор забрал первую цель (карточка: вход 1.2851 → выход 1.3072, +17.19%), msg 222503 |
| | бот: `tp_hit` → `skip no_open_position` — в журнале позиции нет, **тейк пропущен** |
| 25.10 07:07 | реконсиляция каждые 10 минут пишет `unknown_position` в `audit_log` — туда никто не смотрит |

Позиция на 1010 USDT жила на бирже двое суток без единой строки в `trades`/`orders`/`actions`.
Стёрся даже `normalized_text` — в UI сообщение выглядело пустым.

## Корневая причина

`pipeline.ts::processMessage` исполняет все интенты сообщения внутри ОДНОЙ транзакции БД.
Ордер, уже принятый Bybit, откатить нечем — а `BybitApiError` из второго интента откатывал
журнал первого. Граница отката проходила по сообщению вместо биржи.

Таких сообщений в истории **7**, и все семь потеряли журнал целиком (`actions=0`,
`normalized_text=NULL`): 4× retCode 34040 (30.07, 19.08, 2× 02.09) и 3× 110007 (22.10, 22.10, 24.10).

## Фикс (327cf52)

Отказ биржи по существу стал терминальным исходом СВОЕГО действия, а не всего сообщения:

- `actions.status='failed'` + текст отказа в `detail` (статус `failed` был в enum и не писался никем);
- сделка этого действия отменяется, **только если под ней нет ни одного ордера** — строка `orders`
  пишется строго ПОСЛЕ успешного ответа биржи, её наличие означает живую экспозицию (такую
  поднимает реконсиляция по orderLinkId);
- сообщение → `needs_review` + `exchange_rejected_<retCode>`, с сохранённым текстом и
  исполненными соседними действиями.

Сеть/БД по-прежнему пробрасываются наружу: транзакция откатывается целиком, сообщение остаётся
`received`, следующий тик повторит — задвоить ордер не даёт идемпотентность по orderLinkId (110072).

Тесты: два новых в `pipeline.test.ts` воспроизводят живой инцидент (отказ на втором действии и на
первом). Весь движок — 711 зелёных, `pnpm -r typecheck` чист.

## Восстановление журнала и доставка тейка

Позиция восстановлена по бирже (скрипт-разовик, ни одного вызова, меняющего состояние биржи):
сделка **TR-1152**, 778.2 XRP @ 1.285, стоп 1.1693, ордера `K02-222468-00-E0`/`-S0`, зеркало
позиции, обе строки `actions` сообщения 222468 (XRP executed, DOGE failed) и его текст.
Доказательство принадлежности — филл в `executions` с нашим `orderLinkId` и размер ровно по
настройке канала (trade_size 100 × плечо 10 ÷ 1.285 = 778.2).

Сообщение 222503 переиграно штатным путём: `tp_hit` → закрыта треть, **259.4 XRP @ 1.3006**,
+4.05 USDT брутто / +3.71 нетто. Автор взял эту же треть на 1.3072 — опоздание стоило ≈1.7 USDT.
Остаток 518.8 XRP под защитным стопом 1.1693.

Реконсиляция больше не кричит `unknown_position`: `flagged=0`, `reattributedExecutions=2`.

## Аудит остальных путей на тот же класс

| путь | вердикт |
|---|---|
| интенты сообщения (`processIntent`) | **был дефект — исправлен** |
| TTL-свип лимиток (`main.ts`) | одна транзакция на ордер, отмена идемпотентна, ошибка логируется |
| уборка после полного закрытия (`finalizeClosedPositions`) | вне транзакции, обе ветки в try/catch |
| перенос защитного стопа (`private-ws.ts`) | сетевой вызов вне транзакции, ошибка логируется |
| отмена осиротевших ордеров (`reconcile.ts`) | в try/catch |
| таймаут/сеть на `createOrder` | ретрай реконструирует тот же orderLinkId → 110072 = идемпотентный успех |

## Осталось (решает владелец)

1. **Деплой фикса не выполнен** — `docker compose up -d --build engine` заблокирован
   классификатором. На сервере лежит нужный коммит, движок крутит старый код.
2. **Сигнал о неатрибутированной позиции не доходит до оператора.** Реконсиляция пишет
   `unknown_position` только в `audit_log` — ни UI, ни `needs_review`. Два дня крика в пустоту.
   Атрибуцию при этом можно было решить детерминированно: `orderLinkId` (`K02-222468-00-E0`)
   кодирует и канал, и сообщение, и филл с ним лежал в `executions`.
3. **Модель противоречит сама себе на `тейк <цена>` с карточкой.** В msg 222503 `ai_summary`
   говорил «first target hit at 1.307 (+17.19%)», а действие было выписано `tp_set` — то есть
   зафиксированную автором прибыль бот превратил бы в висящий лимитник. Живая перепроверка
   24.10→25.10 дала разные ответы на один текст. Нужна своя петля с golden-тестами.
4. **Свободная маржа считается по снапшоту раз в 30 с** и не уменьшается на ордера, выставленные
   этим же сообщением — прямой триггер 110007 на многомонетных сообщениях.
5. `trades.size` не уменьшается при частичной фиксации (обе ветки пишут только `status`) —
   чинится периодической реконсиляцией в пределах 10 минут. На сайзинг не влияет
   (`resolveLadderBasis` считает по `trade_legs`/зеркалу), поле отчётное.
6. Из прошлых лупов: двухмонетные строки в `ch2.adapter.ts` (цена второй монеты прилипает к
   первой), привязка ключа Bybit к IP 149.202.63.170, ~12 старых `needs_review` (июль—1 окт).
